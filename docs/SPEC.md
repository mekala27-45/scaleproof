# Scaleproof scope

Day 31, assigned November 16, 2026. Research and implementation started November 13, 2026 in America/New_York.

Scaleproof asks whether a CPU-driven Kubernetes HPA improves deadline success for one pinned retrieval workload on one shared host. A negative measured result is valid. Missing mandatory execution is incomplete.

The CPU lane uses an immutable ONNX BGE small bundle, all 24 original synthetic notes, one inference thread, a bounded queue of eight, and fresh query encoding for each request. Twelve development requests select rates. Twelve reserved requests supply the frozen study. Reserved outcomes never tune a rerun.

The fixed lane has one replica. The HPA has one to three, a 250 mCPU request per pod, a 500 mCPU limit and a 70 percent target. Each of three matched pairs uses the identical seeded open-loop schedule. Pair order alternates. Each run lasts 720 seconds: warmup 0-60, low 60-180, high 180-480, low 480-660 and no-arrival drain 660-720. Client deadline is five seconds from scheduled time.

The primary result is high-phase completed-before-deadline arrivals divided by all scheduled high-phase arrivals. Dispatch failures, timeouts, rejects and unfinished work remain in that denominator. Successful latency percentiles are supporting observations and always retain their sample count. Replica-seconds integrate the observed step function over 60-660 seconds.

The public FastAPI policy has no inference, scheduling or cluster route. It validates a bounded numeric plan and writes a session-scoped receipt to PostgreSQL. Replays return the same receipt. Conflicts and physical attempts remain separate.

The React reader displays Workload, Capacity, Requests and Method. Planned, deterministic local, deterministic live and recorded evidence remain visibly distinct. Missing evidence is an explicit state.
